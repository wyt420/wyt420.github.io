## 大马力 MES：从“功能能用”到“工作台好用”

MES 业务模块很多，传统树形菜单虽然完整，但用户需要记住层级和入口。桌面端与 Web 端的改造因此采用了相同的设计语言：**保留原菜单作为唯一数据源，在展示层增加工作台与磁贴导航**。

### 桌面端：复用 Prism Region 中的菜单

WPF 客户端没有再维护一份磁贴配置，而是由 `NavigateMenuCatalog` 扫描 Prism Region 中已有的 `MenuItem`，将其映射成工作台分组。点击磁贴时仍触发原菜单事件，因此计划、生产、质量、设备等业务模块不需要跟着改造。

同时通过事件总线处理 Shell 初始化、菜单刷新和模式切换，并把顶栏、Tab、侧栏等样式集中到主题资源中。这次改造的价值不只是视觉升级，更重要的是把重构范围控制在壳层，降低了工业客户端的上线风险。

完整实现见：[MES 桌面客户端 Shell 重构](/posts/2026/05/mes-shell-workbench-refactor/)。

### Web 端：动态路由同时驱动树形菜单与应用中心

Web 端菜单来自后端权限接口。`useMenuRoutes` 与 `menuFlatten` 从权限路由树构建树形菜单和磁贴分组，解决了权限变化后两份配置容易不一致的问题。首页的 KPI、待办、快捷入口和计划模块可以排序、隐藏，相关偏好按用户持久化。

在交互上还处理了平铺模式预加载、旧布局配置迁移、动态路由 path 与 name 不一致等问题。业务页面保持零侵入，但入口查找和跨模块切换明显更直接。

完整实现见：[MES 智造云 Web 前端重构](/posts/2026/05/mes-cloud-web-refactor/)。

## EAM：围绕真实业务闭环持续打磨

EAM 的近期工作不像 MES 那样集中在一次界面重构，而是分布在资产、物资、维修和检修等多个业务闭环中。

### 物资与编码

- 修复编码修改申请中分类数据加载时序问题，避免表单先渲染、基础数据后到达造成空分类。
- 在物资编码库中约束不允许直接修改的状态，防止绕开正式流程改变主数据。
- 修复盘点任务重复提交，并处理同一仓库存在多个保管员时操作按钮权限判断不完整的问题。

### 外委维修与审批

- 补齐验收审批必须选择明细的前端校验。
- 修复取消操作在未选择明细时仍可提交、同一业务可重复取消的问题。
- 处理取消后重新申请时预算价格被历史状态错误影响的后端逻辑。

这类问题的共同点是：按钮是否可用、表单是否可提交，不能只看当前页面字段，还要结合流程状态、明细选择和历史操作一起判断。

### 设备台账与移动检修

- 信息化设备台账增加按科室名称查询，前后端同步扩展查询条件。
- 移动端修复计划检修的成本中心、人员选择和实际工时计算。
- 登录失败时展示后端返回的具体信息，避免只有“异常”却没有可诊断线索。
- API 对需求计划中的可选子类增加空值保护，避免量检具校验触发空指针。

更多细节见：[EAM 三端持续交付实践](/posts/2026/08/eam-multi-end-delivery/)。

## 这段开发带来的几个认识

### 1. 单一数据源比“快速复制”更重要

MES 的菜单、EAM 的分类与状态字典都说明了同一件事：展示层可以有多种形态，但业务数据最好只有一个可信来源。复制一份配置短期更快，后续一定会付出同步成本。

### 2. 企业系统的大多数 Bug 都发生在状态交界处

正常新增通常不是最难的，取消后再申请、多人保管、重复点击、基础数据尚未返回、历史配置仍存在，才是更容易出问题的路径。开发时需要主动覆盖“未选择、重复执行、状态回退、异步未完成”这些边界。

### 3. 多端一致不是界面长得一样

桌面端、Web 端和 App 的组件体系不同，强求像素级一致没有意义。真正需要一致的是业务概念、入口命名、校验规则和错误反馈。用户在不同终端处理同一业务时，不应该重新学习一套规则。
